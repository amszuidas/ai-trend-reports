## 今日 Feature 趋势摘要

1. **Agent Skill 正从提示模板变成交付工作流。** Diagram Design 不只给出审美提示，还交付品牌 onboarding、旧图导入、尺寸/受众取舍、静态/动态输出与自检；PPT Master 则把叙事、素材、原生 PPTX、动画、旁白和 QA 串成成品流程。
2. **多 Agent 产品已明显分层。** Orca 管“开发者如何并行运行和审阅 Coding Agent”；Paperclip 管“组织如何分工、预算、审批和审计 AI 员工”；Agency Agents 只是可安装角色/SOP 资产。三者不能仅凭“多 Agent”互相替代。
3. **上下文层的重点从召回走向问责。** Semantica 把决策、因果、规则、PROV-O 与双时态变为一等对象；RAGFlow 则把解析、人工修 chunk、检索测试、引用与 Agent workflow 做成一体化工作台。
4. **模型路由开始关注 Agent 所处阶段。** Switchyard 可按内容分类、探索/恢复/收敛信号或先弱后强升级选模型，而不只做静态 provider fallback；但 v0.2.0 明确仍是 pre-alpha，治理与生产网关能力不完整。
5. **端侧模型开始把“能调用工具”做成受约束产品面。** Needle 2 以 14MB 单文件、schema grammar、工具检索和约 28MB 会话内存瞄准设备端；但 grammar 只保证结构，confidence 只是信号，真实动作的审批、幂等和回滚仍由宿主负责。
6. **多模态开源正在同时补“生成、精修、训练”。** LTX-2.5 不只做文本/图像到同步声画，还提供 Retake、关键帧/控制、ComfyUI 与 LoRA/IC-LoRA/全量训练；相应代价是约 66GiB gated 权重、较高算力和自定义商业许可边界。
7. **Release surface 漂移仍是今日最大采用风险。** Paperclip stable 落后 master 384 commits；Semantica v0.6.5 后有 28 个修复；Orca 最新 stable 已到 v1.4.181、官网 changelog 尚滞后；Kronos、Diagram Design、Agency Agents、Needle 缺统一 GitHub Release 契约。

| MCP 发布/消费 | Java 方法/Goal 暴露给客户端，也消费浏览器/GitHub等 MCP tools → 接工具生态 | transport 文档口径漂移，安全 profile 需实测 |
| A2A | Agent Card、消息、任务/streaming server → 跨系统互操作 | v1.5.0 有模块但文档薄；不等于 future federation |
| 多 LLM / BYOK / 本地模型 | OpenAI/Anthropic/Gemini/DeepSeek/Ollama 等，动作级选模型 → 成本/隐私可分层 | provider 能力不等价，用户自备 key/算力 |
| Shell / templates / Tripper | 交互执行、项目脚手架、分级 examples 和旅行 demo → JVM 新手可复现 | examples snapshot 可能与 stable 不同；Tripper 需 Docker/keys |
| Observability / Testing | OTel/Micrometer 导出 Langfuse/LangSmith/Zipkin/Prometheus，fake LLM 测试 → 路径/成本/错误可查 | backend 需额外部署；Eval 当前仅占位，不是成熟评测平台 |

**成熟度、同类与缺口：**Latest [v1.5.0](https://github.com/embabel/embabel-agent/releases/tag/v1.5.0)（2026-08-11）。Evolving 模式、跨 Embabel/第三方 federation、若干 Grafana/guardrail/eval 能力仍是 future/coming soon。相比 LangGraph，Embabel 强在 JVM/Spring/领域类型与动态 goal/action 组合，弱在生态、可视调试、持久 checkpoint；相比 CrewAI，企业 Java 可控性强、角色/任务上手素材弱；相比 Spring AI Alibaba Agent Framework，Embabel 目标/条件组合与三模式突出，对方在 Spring AI/Graph 工作流生态更贴近阿里体系。

**今日关注：****事实**：榜单 #16、+40，v1.5.0 刚加入新 provider/集成与可靠性改进。**推断**：JVM 企业团队需要原生而非 Python sidecar 的 Agent 框架；“动态规划”不等于自治流程已天然安全或可恢复。

### 17. [cactus-compute/needle](https://github.com/cactus-compute/needle)

**一句话定位：**给手机、穿戴、家居和机器人上的极小设备一个离线工具调用/结构化提取模型，用极小内存返回 schema 约束的 JSON；它不是通用聊天模型，也不负责安全执行真实动作。

**典型场景：**设备控制意图转函数调用；离线表单/票据提取；大工具目录检索；低置信度升级云端/人工；用私有工具数据做 LoRA。

| Feature | 能做什么 → 用户价值 → 场景 | 状态 / 条件 |
|---|---|---|
| 14MB 单文件 / 约 28MB session | 权重和 engine 打包、推理无网络 → 极小设备可离线 | 厂商自报；首次 engine 从 HF 获取并缓存，平台/芯片需实测 |
| Python decorator / schema tools | 函数签名/docstring 或 JSON schema 声明工具 → 低代码接入 | `pip install cactus-needle`；宿主仍负责权限和函数安全 |
| Grammar-constrained JSON | 从 schema 编 grammar 限制 token → JSON/字段结构不破 | 只保证结构，不保证参数真实、合理或授权 |
| Multi-step calls | 执行结果回填后继续下一工具，直到 respond → 能完成联系人搜索→发消息等链 | 真实副作用、幂等/超时/回滚由宿主处理 |
| Structured Extraction | 将记录 schema 当唯一工具，返回 typed arguments → 文本到票据/表单 | 结构合法不等于识别值正确 |
| Tool Retrieval | 大目录每轮只渲染 top-5 工具并缓存 index → 控制上下文/内存 | 召回错会让正确工具根本不在候选；需领域评测 |
| 256-token bounded memory | 滑窗 + pinned tools，长会话内存近常数 → 设备端可预测 | 长距离细节会丢；不是持久记忆 |
| Confidence 输出 | 每次返回校准头分数 → 宿主可自行决定执行/升级 | 当前 API **没有自动 threshold gate**，最新提交明确移除 gate；需用户写策略 |
| Playground | 浏览器编辑 tools/prompt、连续对话 → 快速体验/调试 | 本地服务；不是托管多用户产品 |
| UI 一键 finetune / LoRA / export | 对当前工具数据训练并下载 `.cact` → 适配私有 schema/说法 | 训练仍需数据、算力与验证；一键不等于质量自动保证 |
| Refusal / no free-text fallback | 无适配工具输出空 call，最终结果基于 tools → 行为面更窄、可预测 | 不适合开放问答；拒绝准确率需自测 |

**成熟度、同类与缺口：**main 与 tag v2.0.2、PyPI 2.0.2 对齐，但 GitHub 没有 Release notes/稳定发布契约。14MB、28MB、4300/850 tok/s 和 benchmark 均是项目/模型卡自报，需在目标硬件与自有 tools 上复跑。相比 FunctionGemma 270M、LFM2.5 230M、Apple FM，尺寸/内存极小、grammar/tool retrieval 更聚焦，但通用语言能力、上下文和生态更窄；相比云函数调用，隐私/离线/固定成本强，模型质量、更新、监控和复杂长上下文弱。

**今日关注：****事实**：榜单 #17、+315，2.0.2 代码/包已提供完整本地 POC 面。**推断**：Agent 从云端走向 device-use 后，14MB 的清晰约束很有传播性；性能图、置信度和 schema 均不构成对真实动作安全性的证明。

## 今天最值得体验的 3 个项目

1. **[Diagram Design](https://github.com/cathrynlavery/diagram-design)**：最快得到可见价值。最吸引人的不是图表数量，而是网站品牌 onboarding、draw.io/Mermaid 重绘 ledger、受众/尺寸旋钮和静态优先 Motion。适合用一张真实旧架构图验证它是否真的能“编辑”而非只换皮。
2. **[PPT Master](https://github.com/hugohe3/ppt-master)**：最完整的 Agent 内容交付工作流。建议用一份有来源的 5–10 页报告试“native DrawingML + data-backed chart + Live Preview”，重点检查事实、元素可编辑性和跨 PowerPoint/Keynote 兼容，而不是只看截图。
3. **[Needle 2](https://github.com/cactus-compute/needle)**：最有辨识度的端侧实验。用 5–20 个真实工具在 Playground/Python 中测 tool recall、arguments、off-topic refusal 与 confidence 分布；执行前自行做阈值、审批、幂等和回滚，切勿直接把模型输出接高风险动作。

若更关心团队治理而非即时体验，优先试 Paperclip 的 heartbeat + 预算硬停 + 审批；若更关心企业知识库，则用 RAGFlow 对一批复杂 PDF 做“解析—人工 chunk—retrieval test—引用”全链验证。

## 值得持续跟踪的新 Feature 方向

1. **Agent 原生成品格式**：Skill 不再只返回文字，而是带导入、品牌、交互预览、质量 gate、可编辑 native object 和多渠道导出的完整 deliverable contract。
2. **Release Surface Manifest**：同一项目的 repo、package、desktop、web、extension、model weights 与 docs 需要机器可读地声明版本和能力；今天的 Orca/Enjoy/Paperclip/Kronos 已显示这是现实痛点。
3. **Stage-aware Model Routing + 硬治理**：把 Switchyard 的阶段识别与 LiteLLM/Paperclip 一类 auth、预算、rate limit、审批、failover 结合，才可能形成生产 Agent gateway。
4. **可撤销的设备端动作**：端侧 grammar、tool retrieval 与 confidence 必须继续补 capability grants、风险分级、幂等 key、dry-run、approval 和 rollback，不能把合法 JSON 当安全动作。
5. **Decision/Provenance 原生化**：将 Semantica 的决策、先例、来源、双时态与规则接入 RAG/Agent control plane，让“为什么做、依据何时有效、谁批准”成为通用对象。
6. **多 Agent 三层控制面**：执行层（Orca）—组织层（Paperclip）—能力资产层（Agency Agents/Skills）需要更清晰的协议与可移植 ledger，而非每层各自重复 Agent 定义。
7. **多模态的局部可修复性**：LTX-2 的 Retake、PPT Master 的局部页重生、Diagram Design 的重绘 ledger 都指向同一方向：用户更看重“只修坏的部分并保留其余产物”，而不是每次全部重生。
