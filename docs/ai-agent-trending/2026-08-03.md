## 今日 Feature 趋势摘要

1. **AI 教育资源仍能压过工具型项目。** `AI-For-Beginners` 以 +2,629 位居榜首，`generative-ai-for-beginners` 也再次上榜；前者是符号 AI、双框架深度学习、CV/NLP/RL 的基础课，后者才覆盖 Prompt、Function Calling、RAG、Agent 与模型 API。课程名相近，不代表功能时代和目标相同。
2. **Agent 的互联网能力正在从“浏览器自动化”拆成可安装的渠道包。** `Agent-Reach` 负责给 Agent 装配和体检网页、社交、视频与 GitHub 上游工具，`last30days-skill` 聚焦最近 30 天的多源研究；两者共同说明用户更在意“能访问哪些真实来源、登录态怎样处理、证据能否回链”，而不是再要一个泛化聊天入口。
3. **Skill 正同时走向专业化与地域化。** `reverse-skill` 把安全任务路由、工具自举、授权和证据交付连成闭环，`k-skill` 则把韩国公共数据、生活、文书和业务流程封装给 Agent。目录数量不是成熟度，真正门槛在第三方站点稳定性、宿主兼容、凭据和法律边界。
4. **Agent 产品层开始竞争“工作桌面、能力分发和团队记忆”。** OpenWork 把本地文件、浏览器、SaaS、Skills/Plugins/MCP 与团队 Marketplace 放进桌面 UI；TencentDB Agent Memory 把聊天、SOP、文档和代码上下文变成可治理资产；Reasonix 则从终端编码 Agent 延伸到 TUI、桌面和 VS Code。
5. **本地推理出现两种截然不同的价值取向。** AirLLM 用磁盘与时间换极低峰值显存，甚至让 2.8T checkpoint 在单卡上完成 token 生成，但实测约 292 秒/token；DwarfStar（ds4）则围绕少数最新开源模型交付本地 Server、Coding Agent 和多硬件后端。一个回答“能不能跑”，另一个更接近“能不能用”，都不能直接替代通用高吞吐服务框架。
6. **今天最需要删除的营销等式是：4GB ≠ 只需 4GB 总资源；零 API 费 ≠ 零成本/零风控；支持 MCP ≠ 所有客户端均验证；Browser ≠ 全桌面 Computer Use；目录已存在 ≠ 已进入稳定 Release。** 今日多个项目的真实价值依然成立，但必须连同这些边界一起看。

### 2. [lyogavin/airllm](https://github.com/lyogavin/airllm)

**一句话定位：** 面向显存很小、但有足够磁盘且能容忍极低生成速度的研究者，让远超显存容量的 Hugging Face 大模型在本地完成推理和可行性验证；重点是“能跑”，不是实时可用。

**典型场景：** 在 4–12GB 显存上验证 70B/405B/671B/2.8T 模型；离线或隔夜小批量任务；采购 GPU 前验证模型行为；Apple Silicon/CPU 私有实验；跟进 Kimi K3、DeepSeek-V3、Qwen3 等最新 checkpoint。

| Feature | 能做什么 → 用户价值 → 适用场景 | 状态 / 边界 |
|---|---|---|
| **超低显存大模型推理** | 让模型总权重远大于 GPU 显存，README 示例含全精度 70B 约 4GB、405B 约 8GB → 小卡也能验证超大模型 → 可行性测试 | 核心可用；这是峰值 GPU 显存，不是总资源需求 |
| **Kimi K3 2.8T 单卡运行** | v3.1.0 完成真实 token 生成，官方测得 3.72GB 峰值显存 → 把极端 MoE checkpoint 纳入单机验证 → 前沿兼容研究 | 同一测试约 900 秒初始化、292 秒/token、checkpoint 约 1.56TB；只测短提示，[PR #316](https://github.com/lyogavin/airllm/pull/316) |
| **多模型家族覆盖** | README 列 Llama、Qwen、DeepSeek、Mistral/Mixtral、Phi、Gemma、ChatGLM、Baichuan、InternLM、Yi → 同一入口横向试用 → 模型选型 | “几乎所有热门模型”是维护者概括，不代表每个变体都有验证矩阵 |
| **统一 `AutoModel`** | 传 Hugging Face repo ID 或本地路径自动选择加载入口 → 少切换专用类 → Notebook/快速试模 | v3 可用；受限模型仍需 HF token，[Quickstart](https://github.com/lyogavin/airllm#quickstart) |
| **接近 Transformers 的 Python 体验** | 继续使用 tokenizer、`generate()` 与 decode → 现有研究脚本改造较小 → Python 实验 | 只有 Python/Notebook 面；无正式服务 SDK、统一 CLI 或 Web UI |
| **原生 dtype、FP8 / MXFP4 checkpoint** | 直接尝试 DeepSeek-V3、Qwen3-FP8、Kimi K3 等官方格式 → 减少另行转换门槛 → 新模型验证 | FP8 在 v3.0、K3 MXFP4 在 v3.1；各模型依赖仍不同 |
| **可选 4/8-bit 压缩** | 通过 `compression` 减少读取量和存储 → 部分磁盘受限任务更快 → 空间/吞吐权衡 | 需 `bitsandbytes`；“最高 3 倍”是旧版自报，缺当前统一 benchmark |
| **CPU 与 Apple Silicon 路径** | 支持 `device="cpu"`，macOS 提供 MLX Notebook → 无 NVIDIA 也能做本地验证 → 私有/离线实验 | macOS 只明确支持 Apple Silicon；速度仍以“可运行”为主 |
| **磁盘与缓存控制** | 指定拆分目录、本地模型路径，并可只保留处理后副本 → 控制超大 checkpoint 的落盘位置与双份占用 → SSD 工作站 | 首次下载/处理仍需巨量磁盘和网络，删除原件前应确认可恢复 |
| **Prefetch 与 Profiling** | 开预取、打印耗时 → 判断瓶颈在磁盘、搬运还是计算 → 硬件调优 | README 注明 prefetch 仍只适用于部分 Llama2 路径，不可泛化 |

### 10. [antirez/ds4（DwarfStar）](https://github.com/antirez/ds4)

**一句话定位：** 面向高内存 Mac、DGX Spark、Strix Halo 或多卡工作站用户，把 DeepSeek V4 Flash/PRO 与 GLM 5.2 的本地推理、长上下文、工具调用、API 服务和 Coding Agent 做成一套高度专用环境；它明确不是通用 GGUF 引擎。

**典型场景：** 在 96/128GB+ Apple Silicon 上离线 Coding/文档任务；用 SSD streaming 在内存不足时换取可运行；两台 Mac 汇总内存或降低 decode 延迟；4/8 张 L40S 服务多用户；用原生 Agent 或接 opencode/Pi/Codex/Claude Code。

| Feature | 能做什么 → 用户价值 → 适用场景 | 状态 / 边界 |
|---|---|---|
| **专用模型/量化下载** | `download_model.sh` 获取核验过的 DeepSeek V4 Flash/PRO、GLM 5.2 GGUF → 少判断兼容格式 → 高内存本地部署 | 只接受列出的布局；任意 GGUF/Safetensors 不能直接加载 |
| **SSD 专家权重流式** | 在 Metal 和部分 ROCm 路径把权重留 SSD、按需缓存 → 内存不足仍能跑 MoE → 64GB Flash/128GB PRO 实验 | 容量解法，不是免费加速；生成比 prefill 更易受 cache miss 影响，PRO/128GB 为实验性 |
| **Pipeline Parallelism** | 跨机器分层、汇总内存并流水长 prompt → 单机放不下也能启动 → 两 Mac 跑更大模型 | 逐 token 必经整链，README 实测两 Mac 生成反而慢约 19.4%；协议无认证/加密 |
| **两 Mac Thunderbolt/RDMA TP** | 两 GPU 同时处理 token，各驻一半专家，RDMA 不可用退 TCP → 相比单机 SSD 降 decode 延迟 → 双 M5 Max/M3 Ultra | 固定两机 50/50、同代码/GGUF和系统配置；仅 `ds4` CLI，不支持 Server/Agent |
| **CUDA 多卡 + 多会话批处理** | DeepSeek 在偶数 GPU 切分，并用 `--batched-session` 常驻多 KV 会话 → 把旧 Ada 工作站变团队节点 → 4/8×L40S | 部分形状会退 exact fallback，仅公平并发而非同等吞吐；GLM/DGX 路径不同 |
| **原生 Coding Agent/TUI** | 内置读/搜/改/写、bash、Google Search/visit page，支持队列、Markdown、会话保存/切换和 KV 恢复 → 无额外 API hop 的本地编码闭环 → 私有仓库 | 已能用但 README 明说离 prime time 仍远；网页工具需联网/Chrome授权 |
| **OpenAI / Responses / Anthropic API** | 提供 Chat/Completions/Responses/Messages 与 SSE thinking/text/tool-call streaming → 现有客户端可接本地模型 → Coding Agent 服务 | 是协议子集，`model` 只是当前 GGUF 别名；无任意切模/完整平台/strict structured output |
| **磁盘 KV Cache** | 保存 prompt token、KV、logits、tool-id，切会话/重启只算后缀 → 大幅减少 25k 初始提示重复 prefill → 长 Agent 会话 | DS4/模型布局专用，不是可移植通用快照；多会话需显式开启 |
| **Thinking + DSML 工具调用** | 支持 non-thinking/thinking/Think Max，并精确回放历史 DSML → 减少长工具会话前缀失配 → Agent/函数调用 | Think Max 受 context 建议限制；通用 schema-constrained output 仍是 Issue |
| **DSpark / MTP 推测解码** | 用 support GGUF 提议未来 token、主模型验证 → 可预测代码可能减少 decode 步数 → greedy coding | 实验、opt-in；不加速 prefill/采样，低接受率可能更慢，PRO 不支持 DSpark |
| **功耗与方向控制** | `--power` 权衡温度/风扇/速度，steering 改冗长或拒答倾向 → 适配笔记本长跑/研究 → 本地 Agent | GLM 仅 power 100 且不支持 steering；steering 不等于质量提升 |
| **Bench / Eval / 质量回归** | 输出 context frontier 性能 CSV，用 92 题和 continuation/logprob 工具比较量化 → 在自己硬件验证速度/明显退化 → 选 quant | 是项目内精选回归和自报方法，不是独立 GPQA/AIME/安全榜单 |

**开箱/硬件/付费：** 需从源码构建并下载公开 GGUF；CLI、server、SSE、tool calls、Agent、disk KV、bench/eval 均有命令。Flash q2 建议 96/128GB，q4 ≥256GB，PRO q2 常规建议 512GB；64GB 需 SSD streaming；1M context 仅 KV/indexer 约多 26GB，96/128GB 更现实是 100k–300k。两 Mac TP 要 Thunderbolt/RDMA 与系统设置；CUDA sweet spot 是项目自报的 Q2 4×48GB 或 Q4 8×48GB；ROCm 主要验证 Strix Halo，CPU 只适合参考/调试。代码/公开 GGUF 无功能付费墙，网页工具和第三方客户端可能有各自成本。

**同类与易用性：** 相比 llama.cpp，DwarfStar 强在少数模型的 SSD streaming、DSML 回放、磁盘 KV Agent、双 Mac RDMA 组合，缺通用 GGUF/VLM、广泛后端、Web UI、embedding/rerank、多模型 router 和 structured output；相比 vLLM，它更适合高内存个人机/特定老卡和原生 Coding Agent，缺模型广度、生产扩缩、LoRA、多模态、监控与成熟服务生态；相比 MLX-LM，它跨 Metal/CUDA/特定 ROCm且 Agent/Server 更完整，缺 Python SDK、HF 任意模型、量化上传和微调。现有界面是 CLI/TUI/API，无 Web UI、正式 SDK/共享库、包管理安装或托管 Demo；文档和 QA/测量命令很丰富。

**限制与今日关注：** 整个项目明确 Beta、快速变化，且 [Releases](https://github.com/antirez/ds4/releases) 没有任何正式发布/tag，用户实际跟随 main。SSD streaming 解决容量但可能让逐 token 很慢；pipeline 汇总内存却通常让生成变慢；1M context、批处理和速度数字都依模型/量化/context/硬件/backend，不能泛化。“2-bit 仍高质量”主要来自项目方回归，不是独立综合评测。没有任意 GGUF/Safetensors、多模态、embedding/rerank、LoRA/训练、schema constrained output、Web UI、正式共享库或 Vulkan。**事实**：当前功能已覆盖三硬件后端、Server、Agent、SSD/跨机/多卡与 QA，今日 +139，但无 Release。**推断**：在 64–128GB 个人设备或消费级组合上跑最新大模型的硬件玩法、antirez 的影响力和内置 Agent 共同放大传播；不应解读为 vLLM 式生产成熟。

### 11. [esengine/DeepSeek-Reasonix（Reasonix）](https://github.com/esengine/DeepSeek-Reasonix)

**一句话定位：** 面向希望在本机、终端、桌面或编辑器里自主完成代码探索、修改、验证和长周期任务的开发者，提供一个 MIT、多 Provider、强调长会话成本意识与可控执行边界的 Coding Agent。

**典型场景：** 跨文件修 Bug 并跑测试/审 diff；用 Plan/Planner-Executor/Delivery 做高风险实现；用 Goal/AutoResearch 持续排障；用子 Agent 并行探索/评审；从 Desktop、Web、VS Code、SSH 或飞书/Lark/微信/QQ 继续本机工作流。

| Feature | 能做什么 → 用户价值 → 适用场景 | 状态 / 边界 |
|---|---|---|
| **CLI/TUI + Desktop + Web + VS Code** | 交互 TUI、headless `run`、桌面会话/diff/终端/审批、`serve` 浏览器 UI、ACP 编辑器接入 → 同一引擎覆盖多入口 → 本地/远程/自动化 | v1.19.3 可用；VS Code 不内置 CLI，需先安装配置 |

| **MCP / Plugins / Skills / Hooks** | 支持 stdio、Streamable HTTP、legacy SSE，Registry 浏览，插件包可携 Skills/Commands/Hooks/MCP，并映射部分 Codex/Claude 格式 → 复用外部生态 → 数据库/浏览器/规范 | 安装/项目声明的 MCP 默认可信；恶意工具仍需 deny 与沙箱 |
| **Resume / Branch / Checkpoint / Rewind** | 会话复制/分支/切换，每轮保存文件快照，可恢复代码、对话或两者 → 降低 Agent 试错成本 → 方案探索 | 不跟踪 Bash、部署、数据库等外部副作用，恢复可能覆盖同时期人工编辑 |
| **Context Engine v2** | 分层加载 `REASONIX.md`/`AGENTS.md`/`CLAUDE.md`，按预算召回项目/全局事实，保留 revision/freshness/归档 → 跨会话少重复说明 → 长期代码库 | 自动召回不是事实保证；仍需维护过时记忆 |
| **逐调用权限 + 文件/进程沙箱** | Ask/Auto/YOLO 与 allow/ask/deny 分离，限制 workspace/可写/禁读，macOS/Linux Bash 可进 OS 沙箱，Provider/Bot 凭据不传子进程 → 控制自治风险 → 本地 Agent | Windows 无 OS 级 Bash 沙箱；获批 Shell 仍以当前用户权限运行 |

**同类与易用性：** Reasonix 最接近 OpenCode：两者均有 TUI/Desktop/IDE、多 Provider、MCP、子 Agent 和权限；Reasonix更突出缓存遥测、Delivery、AutoResearch、IM/SSH 和插件迁移，OpenCode 的 Provider 广度更直接。相比 Claude Code/Codex，它有 Provider 自主和中国 IM 入口，缺托管云任务、Web/Mobile/GitHub 一体化、Automations、语言 SDK 和企业控制面；相比 Aider，它自治/UI/MCP/沙箱更宽，缺成熟 repo map、Git 中心流程、lint/test 自动修复和语音输入。现有 UI 包括 TUI/Desktop/Web/VS Code，文档双语且细；无免安装在线沙箱 Demo。

**限制与今日关注：** 长会话会 snip/prune/compact，不能把 append-only 理解为原文永久驻留；开放 Issue 报告 reasoning 缺硬上限和用户中断后用量统计丢失，UI 成本不等于账单。MCP 安装即授权，readOnly/destructive hint 依赖服务诚实标注；VS Code/ACP 不支持 image/audio prompt，Remote/Windows 沙箱也有边界。**事实**：[v1.19.3](https://github.com/esengine/DeepSeek-Reasonix/releases/tag/v1.19.3) 于 8 月 3 日发布，8 月 1–3 日连续稳定版，当前功能已超过纯终端聊天；今日 +333。**推断**：Go 单二进制、多入口、多 Provider、Goal/Delivery、IM 与“长会话更省”的清晰卖点共同推动传播；缓存比例只能当项目口号，不能当普遍效果。

## 今天最值得体验的 3 个项目

1. **[OpenWork](https://github.com/different-ai/openwork)：最接近“现在就能看到产品价值”的桌面 Agent。** 最吸引人的不是聊天，而是授权目录内的 Workspace/Artifacts、可视 Browser、从对话生成 Skill、Plugin/Marketplace 和一个 Connect MCP 跨客户端复用。建议先用非敏感目录和本地/低成本模型完成“读一组文件→生成报告→保存 Skill”，暂缓连接高权限邮箱或生产 MCP。
2. **[last30days-skill](https://github.com/mvanhorn/last30days-skill)：最适合检验 Agent 研究是否真的“新鲜且有来源”。** `doctor`/`source_status`、互动量排序、跨源聚类、FROM/ABOUT、Discover、drill 和本地研究库形成完整闭环。先用 Reddit/HN/GitHub/YouTube 等基础源研究一个熟悉主题，再人工抽查前十条来源；不要一开始就把 Cookie 和付费 Key 全开。
3. **[Reasonix](https://github.com/esengine/DeepSeek-Reasonix)：最值得开发者比较的本地 Coding Agent 工作流。** Delivery 的验收/证据门禁、Goal/AutoResearch、子 Agent Profile、Checkpoint/Rewind、Desktop/Web/VS Code/IM 多入口和 Provider 可配，已经形成区别于单纯终端聊天的产品面。建议在测试仓库用 Ask/Auto 权限对比 Balanced 与 Delivery，并核对真实 Provider 账单，不要把 UI 的缓存成本估算当最终账单。

> 如果目标是体验“模型能跑到什么极限”而不是日常工作流，可把第三项换成 [AirLLM](https://github.com/lyogavin/airllm) 的小模型 Quickstart，再评估是否值得下载超大 checkpoint；不要直接从 Kimi K3 2.8T 开始。

## 值得持续跟踪的新 Feature 方向

1. **可诊断的 Agent 能力包：** `doctor`、active backend、source status、版本固定和失败降级会成为 Skills/MCP 比“支持多少来源”更重要的产品能力。
2. **团队记忆从向量库升级为可治理资产：** Chat、SOP、Wiki、CodeGraph、Owner/ACL、Loadout、证据回溯和迁移需要在同一控制面协作；TencentDB Agent Memory v2 是值得观察但仍需安全加固的样本。
3. **一次定义、跨 Surface 使用：** OpenWork 的 Connect MCP、Reasonix 的 CLI/Desktop/Web/VS Code/IM，以及插件包兼容，都在争夺“同一能力跨 Agent、IDE、桌面和消息端”的分发层。
4. **长任务的状态、验收和可逆性：** Goal/AutoResearch、Delivery evidence、Checkpoint/Rewind、研究库/Watchlist 表明产品竞争正从“会调用工具”转向“能持续、能复盘、能撤销、能签收”。
5. **本地推理的专业化分叉：** AirLLM 代表极限容量验证，DwarfStar 代表少数模型/硬件的垂直适配；未来要看是否出现兼顾低资源、通用格式、结构化输出、工具协议和稳定服务分发的中间层。
6. **地域 Agent Skill 的合规基础设施：** k-skill 证明本地公共数据/HWP/政务/商业服务有巨大空白，但规模化前提是来源 SLA、法律审查、人工接管、交易审批、品牌/版权和可复现版本。
7. **“近期研究”的事实时效层：** 时间窗、来源时间、互动指标、当前值复核、缓存日期和无日期结果必须显式建模；否则“最近 30 天”仍会被旧索引、抓取失败或来源缺席污染。
