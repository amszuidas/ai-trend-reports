## 今日 Feature 趋势摘要

1. **“Agent Memory”正在从对话检索升级为可治理资产。** TencentDB Agent Memory 把 Chat Memory、Skill、Wiki、CodeGraph 放到同一 Hub，通过 ACL、版本、审核和 Agent Loadout 分发；值得关注的是团队治理，不只是再加一个向量库。
2. **“给 Agent 一台电脑”被拆成持久文件状态与分层执行。** Cloudflare Computer 让一份 Durable Workspace 在受限 Shell、JavaScript isolate 和 Linux Container 间共用；这不是屏幕、鼠标、键盘意义上的 GUI Computer Use。
3. **Coding Agent 的竞争焦点正转向可安装工程制度，而且制度出现三种风格。** `agent-skills` 强在 Define→Ship 的生产覆盖，`mattpocock/skills` 强在人机澄清、领域文档与 tracker-native 长期决策，Superpowers 强在自动触发、worktree、TDD 与逐任务双审闭环。
4. **长任务开始需要独立控制面与可恢复执行合同。** LoopX v0.4.2 新增 child 准入、多 PR Program 与只读 PR 队列观测；Reasonix v1.21.0 则把 Shell 身份、失败阶段、验证状态、流中断重放和会话临时文件纳入可观察执行。
5. **“少给模型无关上下文”正在产品化。** code-review-graph 用本地结构图把变更影响、测试缺口和相关代码通过 MCP/CI 暴露；pdf-inspector 先判断哪些页真的需要 OCR，再本地抽取其余页面。前者减少读库范围，后者减少昂贵 OCR。
6. **Agent 产品从单体聊天转向“创建—精修—复用—持续运行—审计”闭环。** AutoGPT Platform 已具对话建 Agent、可视化 Builder、Marketplace、schedule/trigger 与运行成本面板，但仍是 Beta；最吸睛的 Experts 与语音 onboarding 默认受 feature flag 控制。
7. **今天最应删除的营销等式：** 正式 Release ≠ 产品脱离 Beta；可安装到 70+ Agent ≠ commands/personas/hooks 等价；“Computer” ≠ GUI Computer Use；65× context reduction ≠ 相对熟练 Agent 搜索同样节省；支持 OCR 路由 ≠ 自带 OCR。

## Feature 深度卡片

### 1. [TencentCloud/TencentDB-Agent-Memory](https://github.com/TencentCloud/TencentDB-Agent-Memory)

**一句话定位：** 面向个人开发者与 Agent 团队的自托管“记忆资产中心”，把对话、跑通的方法、文档和代码沉淀为 Chat Memory、Skill、Wiki、CodeGraph，并按权限装配给不同 Agent，减少跨会话/跨角色重复解释与探索。

**典型场景：** Coding Agent 跨 Session 续接项目；把排障/发布/Review 流程沉淀为 Skill；给 Scout/Builder/Reviewer 配不同 Loadout；导入文档、公开代码库和历史会话冷启动；用 ACL 隔离个人、团队与 Agent 专属资产。

| Feature | 能做什么 → 用户价值 → 场景 | 状态 / 边界 |
|---|---|---|
| **L0–L3 Chat Memory** | 把原始对话整理为事实、场景与长期画像 → 新会话少重复交代偏好/决策 → 长期助手、持续开发 | 已发；自动抽取需 LLM，[Memory Core](https://github.com/TencentCloud/TencentDB-Agent-Memory/blob/feat/server_team/MemoryCore/README_CN.md) |
| **Skill 提炼与强制归档** | 从完成任务/工具调用生成带版本、资源、触发、步骤和验证的 SOP → 一次成功变团队经验 → 排障/发布/Review | v2.0.0 已发，强制归档为本版新增，[Release](https://github.com/TencentCloud/TencentDB-Agent-Memory/releases/tag/v2.0.0) |
| **LLM-Wiki** | 从文档生成结构化页面/链接图并全文搜索、沿链接下钻 → 少反复扫整套文档 → 产品/设计/运维知识 | 已发；异步构建且需 LLM，[Knowledge](https://github.com/TencentCloud/TencentDB-Agent-Memory/blob/feat/server_team/MemoryKnowledge/README.md) |
| **CodeGraph** | 索引公开 HTTPS 仓库的文件、符号、调用与影响路径并定时同步 → 改代码前看关联面 → 编码/重构/Review | 已发；私库/SSH 仍未收口 |
| **Memory Hub UI** | 创建 Team/Agent/Task，搜索、审核、版本化、绑定并查看使用次数 → 记忆变成人可治理资产 → 团队运营 | Beta UI；中英文界面可用，[当前 README](https://github.com/TencentCloud/TencentDB-Agent-Memory/blob/feat/server_team/README_CN.md) |
| **ACL 与默认私有** | `private/team/restricted/agent` 可见性和 User/Role/Agent ACL → 共享经验不等于暴露全部记忆 → 多人/敏感上下文 | v2 已发；需正确初始化身份层级 |
| **Agent Loadout** | 按角色绑定资产、优先级与使用方式 → 减少无关上下文噪声 → 研究/开发/测试 Agent 分工 | 已发；不是自动角色规划器 |
| **透明 Memory Proxy** | 兼容 Anthropic `/v1/messages` 与 OpenAI `/v1/chat/completions`，自动注入/回流记忆 → 现有客户端少改代码 → Claude Code 等 | 已发；仍需上游模型与费用，[Proxy](https://github.com/TencentCloud/TencentDB-Agent-Memory/blob/feat/server_team/MemoryProxy/README_CN.md) |
| **分层按需召回** | L2/L3 恢复整体语境，L0/L1 通过只读工具查证，并限制条数/字符/超时 → 降上下文浪费 → 长会话/大历史 | 已发；召回质量受抽取与配置影响 |
| **冷启动导入 + API/SDK** | 从代码、文档、历史 Session 建资产；通过 v2/v3 API、TS/Python SDK 接入 → 旧经验可迁移、自研 Agent 可复用 → 新团队/平台集成 | 已发；完整三件套仍需 Docker/多端口，[安装](https://github.com/TencentCloud/TencentDB-Agent-Memory/blob/feat/server_team/INSTALL_CN.md) |

**开箱/配置/实验：** 三个多架构镜像、`start-all.sh`、Hub、Swagger、SQLite/文件/BM25 可本地起步；记忆抽取、Wiki 和主对话需自备 LLM，Redis/COS/ClickHouse/Langfuse/Opik 是增强项。v2.0.0 是正式 Release，但默认 README 仍写 Team Memory Beta；Codex/OpenCode 原生 Agent Source、私库/SSH、自动路由和完整备份恢复不能算成熟，Knowledge MCP 还有 [#766](https://github.com/TencentCloud/TencentDB-Agent-Memory/issues/766) 的 Header 阻断报告。

**同类、易用性与限制：** 相比 [Mem0](https://github.com/mem0ai/mem0)，它强在四资产统一、团队 UI/ACL/Loadout、代码关系与透明 Coding-Agent Proxy；弱在 provider/vector/framework/CLI/托管生态、简单嵌入体验和公开可复现评测。已有 UI、脚本、API、TS/Python SDK、双语文档和视频；但 Wiki/CodeGraph 非即时、部分客户端需静态维护 task/conversation ID，v2.0.0 仍有源码构建/版本漂移/一键部署问题报告。PersonaMem 48%→76% 是项目方单项结果，不是普遍提升证明。

**今日关注：** **事实**：v2.0.0 于 8 月 3 日发布，今日 #1、+1,057；版本把四类资产、Hub、Proxy 与 SDK 放进同一公开产品面。**推断**：重大版本、腾讯品牌、Agent Memory 热点和可视化 Hub 共同推动传播；热度明显领先于当前生产成熟度。

### 3. [cloudflare/computer](https://github.com/cloudflare/computer)

**一句话定位：** 面向 Cloudflare Workers/Agent 开发者的持久文件工作区 SDK，让 Agent 在同一份长期文件上按需选择轻量 Shell、隔离 JavaScript 或完整 Linux Container；不是有屏幕/键鼠/视觉反馈的 GUI Computer Use。

**典型场景：** Coding Agent 保存代码并跑测试；文档/图片/PDF 生成与短链交付；本地/R2 数据清洗；生成 Git 仓库并交付；在低延迟 isolate 与完整容器之间按任务升级执行能力。

| Feature | 能做什么 → 用户价值 → 场景 | 状态 / 边界 |
|---|---|---|
| **Durable Workspace FS** | read/write/edit/ls/search/stream，重启后仍保留 → 不再把文件状态塞 prompt → 长任务/会话恢复 | Preview 已发；DO Free 单对象 1GB、Paid 10GB，[限制](https://developers.cloudflare.com/durable-objects/platform/limits/) |
| **FS-only 模式** | 不注册执行后端也可保存/处理文件 → 少资源、边界清晰 → 上传/笔记/资产暂存 | 已发；仍需 Worker、SQLite DO、Wrangler |
| **统一多后端 exec** | 同一 `runtime.exec()` 选择 backend 并共享文件 → 无需沙箱间搬运 → 轻重混合工作流 | 已发；当前三种 backend，不含浏览器 |
| **Worker Shell** | Dynamic Worker 中跑 just-bash 与 grep/sed/awk/jq/find → 无 Docker 的快速文本任务 → 搜索/转换 | 已发但依赖付费 open-beta Dynamic Workers，[定价](https://developers.cloudflare.com/dynamic-workers/pricing/) |
| **Worker JavaScript** | 新 isolate 执行 ESM、结构化输入/输出、相对导入与 FS → 比容器更轻 → 数据转换/工具编排 | 已发；默认无公网、仍是实验平台依赖 |
| **Linux Container** | 真实 Linux、网络、Node/Python、包管理器和原生 CLI → 完成编译/测试/转换 → Coding Agent | 已发；线上需 Workers Paid/Containers，本地需 Docker |
| **AI SDK Tools** | 直接生成 read/write/edit/ls 与可选 exec/publish schemas → 少写工具胶水 → 对话/编码 Agent | 已发；需 `ai`/`zod` 与自备模型循环 |
| **Git 工作流** | 无系统 Git 也可 clone/add/commit，Shell 暴露 git → 版本化 Agent 产物 → 修复/生成项目 | 已发；Shell HTTPS 等有能力边界 |
| **R2 / Assets / Artifacts** | 只读挂 R2、上传文件并签短链、每 session 创建 Git repo → 输入/交付统一 → 报告/图片/代码产物 | 需 R2 凭据；Artifacts 仍 beta 权限，[示例](https://github.com/cloudflare/computer/tree/v0.1.1/examples) |
| **事件、终止与同步恢复** | 执行句柄流事件、查询/kill/dispose，可选 observer/tracing，容器同步可重试 → UI 有进度且可恢复 → 长命令 | API 已发；重试/alarm/释放需应用自己接入 |

**开箱/配置/实验：** `@cloudflare/computer` 0.1.1、文件/Git/AI tools 与 8 类示例可试；Shell/JS 需 Loader binding、experimental flag 和付费 Dynamic Workers，Container/Assets/Artifacts/Think 各需对应服务。整个包明确标 **Preview Only / not suitable for production**；`docs/` 是前瞻规格。博客提到浏览器不等于当前 backend；GUI 网页自动化应看独立 [Browser Run](https://developers.cloudflare.com/browser-run/features/human-in-the-loop/)。

**同类、易用性与限制：** 相比 Cloudflare Sandbox SDK，Computer 强在“文件先存在、三种执行共享”，弱在进程/PTY/端口/backup；相比 E2B/Daytona，它更 Cloudflare-native、可 FS-only，却缺 Python SDK、暂停/恢复、快照、桌面、GPU 和成熟控制台。TypeScript API、Vercel AI tools、TUI/Web 示例和教程较完整，无正式管理 UI/CLI/托管 Demo。容器 FS 在内存/FUSE 上，不适合大 monorepo、巨型顺序 I/O 与海量 `node_modules`；Worker Shell 不是完整 Linux，多个 correctness/CI issue 仍开放。

**今日关注：** **事实**：8 月 3 日官方发布 early preview 与 npm 0.1.1，今日 #3、+2,802，为榜单 AI 项目增量第一。**推断**：“computer 不只是 container”的叙事、Cloudflare 品牌和端到端示例放大传播；真正值得跟踪的是 durable workspace + 分层按需执行，而非标题暗示的桌面电脑。

| **双模式表格** | 利用绘图矩形和文本对齐生成 Markdown 表格，处理部分金融/脚注/跨页 → 保行列语义 → 财报/发票 | 已发；高级 TSR 路径需外部结构模型，复杂合并表格会失败 |
| **多栏阅读顺序** | 识别论文/报刊多栏并按栏输出，给 columns/complexity → 少左右栏交错 → 论文/年报 | 已发；复杂视觉版式仍非保证 |
| **CID/Unicode/RTL** | ToUnicode CMap、Type0/Identity-H 与多编码，WASM 内嵌 CMaps → 改善 CJK/RTL → 多语 PDF | 已发；缺/错 CMap 与混合 BiDi 仍可能失败 |
| **Encoding Risk** | `has_encoding_issues` 和 per-page reason 标潜在乱码 → 避免“有字符即成功” → 老 PDF/字体子集 | 只诊断/路由，不修所有编码也不 OCR |
| **Position/Style Items** | x/y/尺寸、字体/字号、粗斜体/下划线/删除线/链接 → 可高亮、引用、区域重组 → 可追溯抽取 | 已发；绑定字段覆盖可能不同 |
| **页选择/处理模式/CLI** | DetectOnly/Analyze/Full，指定页，JSON/raw/compact/items/page markers → 按成本跑所需深度 → 超长 PDF/局部重跑 | Rust/CLI 可用，[Rust API](https://github.com/firecrawl/pdf-inspector/blob/main/docs/rust-api.md) |
| **Rust/Python/Node/WASM** | 后端、脚本、Node/Bun、浏览器本地同类能力，无模型/账号 → 隐私和部署成本低 → 自托管/前端 | WASM 同步，建议大文件放 Web Worker；平台包覆盖不完全一致 |
| **Paired Benchmark Harness** | 固定 corpus/evaluator 比两个 build，并设逐文档回归门 → 团队能验证升级 → 解析器 CI | 已发，[口径](https://github.com/firecrawl/pdf-inspector/blob/main/docs/benchmarking.md) |

**版本与开箱边界：** 无 GitHub Releases；最新 tag `v0.7.0` 是早期 npm 节奏，不能当当前统一库版本。抓取时 Rust crate/root Cargo 为 **0.1.7**、PyPI **0.2.6**、native npm **1.12.0**、WASM npm **0.1.3**；README benchmark 的 0.2.6 对应 Python/benchmark 包。8 月 4–6 日 main 修复未必进入各 registry。Rust/CLI、Python wheels、Node binaries、WASM 均可本地使用；真正 OCR 必须接 Tesseract/Paddle/云 OCR/Firecrawl Hosted 等外部能力，TSR table structure 也可能需外部模型。

**Benchmark 纠偏：** 官方在 200 PDF、OCR 关闭、Apple M4 Pro、五轮中位数上报 overall 0.875、reading order 0.915、table TEDS 0.814、heading 0.788、总时长 0.470s；LiteParse overall 0.873 且 heading 0.811 更高。公开 artifacts 是积极信号，但仍是项目方 corpus/版本/机器，不能外推扫描件、所有语言/复杂版面或端到端 RAG，也不能把 54% 无需 OCR、<200ms 当普遍 SLA。

**同类、易用性与限制：** 相比 PyMuPDF4LLM，强在分类、页/区域路由、encoding reasons 和跨 Rust/Node/WASM；相比 LiteParse，强在窄而快、本 benchmark 的 table/speed，弱在更广文档/OCR；相比 MarkItDown，PDF 深度更强但无 Office/HTML/图片/音频。CLI、四语言 API/类型、浏览器 [Demo](https://firecrawl.github.io/pdf-inspector/) 与 benchmark 可复现，尚无成熟 GUI/REST/MCP。无 OCR/VLM/公式理解、多格式、向量化/分块/RAG；隐藏乱码层、无规则线/合并单元格、复杂标题/CID/BiDi 均可能静默错。

**今日关注：** **事实**：今日 #13、+1,190，7 月 31 日刷新 benchmark，8 月 6 日仍合入 CMap/startxref/OCR 标记/表格与阅读顺序修复。**推断**：“本地极速 + 页/区域 OCR 分流 + WASM + 表格 benchmark”同时击中成本、隐私和 LLM-ready Markdown 需求，Firecrawl 品牌放大传播。

## 今天最值得体验的 3 个项目

1. **[mattpocock/skills](https://github.com/mattpocock/skills)** — 最低试用成本。最吸引人的不是 25 这个数量，而是 `grill-with-docs`、Wayfinder、双轴 review 和 Wizard 把“与 Agent 对齐—长期决策—人工操作”连在一起；Codex 用户应走 npx 路径并接受手工更新。
2. **[code-review-graph](https://github.com/tirth8205/code-review-graph)** — 最容易验证价值。三条命令即可让 MCP/CLI 给出 blast radius、相关测试和最小上下文；先在真实中大型仓库对比 Agent 原本的 grep/阅读成本，不要直接接受 65× 宣传口径。
3. **[pdf-inspector](https://github.com/firecrawl/pdf-inspector)** — 最适合做一小时 PoC。用 CLI/Node/WASM 对自己的报告、发票、论文和混合扫描件跑分类/Markdown，再把 `pages_needing_ocr` 接现有 OCR；它的价值是少做昂贵 OCR，而不是替代 OCR。

> 若关注 Agent 基础设施而非立即落地，今天最值得持续观察的是 Cloudflare Computer；但其 Preview/付费/Cloudflare 绑定使它更适合原型而非生产试用。

## 值得持续跟踪的新 Feature 方向

1. **Durable Workspace + Capability Escalation：** 文件状态先于执行存在，轻量 isolate 失败或不够用时才升级容器/浏览器/GPU。
2. **Governed Agent Memory：** Chat、Skill、文档、代码关系成为有 Owner、ACL、版本、审核、Loadout 和使用反馈的资产，而非全局 prompt。
3. **Long-running Control Plane：** Goal、lease、quota、gate、evidence、material-change cursor、PR Program 和安全 pause/resume 从宿主聊天中解耦。
4. **Skill Capability Contract：** 安装器需要声明 commands/personas/hooks/subagents/references 的真实宿主能力，并用行为 eval 而非“支持 N 个 Agent”证明等价性。
5. **Context Selection as Product：** 代码结构图、页级 OCR 路由、按需记忆和失败后能力升级，目标从“塞更多上下文”转为“只在必要时付更高成本”。
6. **Observable & Recoverable Execution：** Shell 身份/阶段/验证、原子流重放、有限子 Agent 预览、任务监控、checkpoint 副作用边界将成为 Coding Agent 基础产品面。
7. **Agent Marketplace + Human Governance：** Agent-as-Block、Experts、审批门、成本面板、版本回滚与安全试运行会比单纯“多 Agent 聊天”更接近业务采用。
