## 今日 Feature 趋势摘要

1. **Coding Agent 的竞争面正从“模型会写代码”转向“可复用的工作方式与控制面”。** ECC、jcode、OpenWork、Superpowers 和 OpenCodeReview 分别把技能/记忆/安全、轻量多会话终端、跨 Agent 能力分发、软件开发方法论和专用代码审查做成产品级 Feature。
2. **语音 AI 同日出现三种明确产品层次。** speech-to-speech 是可替换的实时语音 Agent 管线；VibeVoice 是长音频 ASR、实时/长篇 TTS 的模型家族；AIRI 则把语音放进可见、会动、能接工具与游戏的虚拟角色应用。三者可组合，但不能互相替代。
3. **本地与边缘 AI 的价值正在从“能运行”推进到“特定硬件上更省资源”。** jcode强调多会话 RAM，VibeVoice 新增 CPU 量化 ASR 路径，FlashKDA 面向 KDA 推理 kernel，ANE 则验证 Apple Neural Engine 上训练；但后三者的硬件、形状、私有 API 或研究成熟度边界很硬。
4. **“确定性流程 + Agent 判断”成为降低噪音的常见功能主张。** OpenCodeReview 用固定覆盖、行号和规则约束包住 LLM Agent；ECC 与 Superpowers用计划、测试、审查和验证步骤约束 Coding Agent。价值在可重复流程，不代表模型判断自动正确。
5. **Agent Skill 正变成知识与方法的可移植交付格式。** Superpowers交付开发方法，ECC交付大规模技能/角色集合，book-to-skill把用户文档转成按需加载技能；下一步关键不是数量，而是来源、版本、宿主兼容与验证。
6. **可视 Demo 与强数字很能驱动 Trending，但最需要降级阅读。** “最省 RAM”“无幻觉”“前沿语音”“开源 Claude Cowork 替代”等表述都要拆成可复现功能、外部依赖、作者自测和缺失项；Faceswap 还必须把功能价值与同意、滥用和硬件门槛同时呈现。

### 筛选说明

- `Snipe-IT` 的 README 确实列出一个社区维护的 MCP Server，但它与 .NET、PowerShell、Jira 等一起属于第三方扩展；Snipe-IT 自身交付的是 IT 资产管理，不能因“可被 Agent 接入”就判定为 AI 项目。

- `awesome-systematic-trading` 收录机器学习书目和库，但仓库自身只是导航；`GeoLibre`、`Pascal Editor` 分别是 GIS 和 3D 建筑应用。它们都可能被 AI 工作流使用，却不直接提供任务定义中的模型、Agent、MCP 或 AI 基础设施能力。
- `FlashKDA` 与 `ANE` 不面向普通终端用户，但分别直接服务模型推理 kernel 和神经网络训练实验，符合“模型训练/推理、AI 基础设施”口径。`ANE` 明确自称研究项目而非生产框架，本报告按边界项处理。

## Feature 深度卡片

### 1. [AIRI](https://github.com/moeru-ai/airi)

**一句话定位：** 面向希望自己拥有并塑造 AI 伴侣/AI VTuber 的用户，把 LLM、语音、Live2D/VRM 身体、屏幕视觉与外部活动放进 Web、桌面和移动角色容器；它的差异不在更强聊天框，而在“角色持续存在”。

**典型场景：** 桌面常驻陪伴；导入 VTuber 资产做角色原型；云端/本地模型切换；围绕当前屏幕内容对话；连接 Minecraft、Factorio 或社交平台做实验。

| Feature | 能做什么 → 用户价值 → 适用场景 | 状态 / 边界 |
|---|---|---|
| **Live2D + VRM 角色** | 导入 2D/3D 模型，控制位置、镜头、凝视、表情与空闲动作 → 复用既有 VTuber 资产 → 桌宠/角色直播 | **已可用**；旧 Live2D 格式不支持，导入仍有兼容摩擦，[配置手册](https://airi.moeru.ai/docs/en/docs/manual/tamagotchi/setup-and-use/) |
| **透明常驻桌面** | Controls Island、托盘、置顶、移动/缩放、自动淡出与点击穿透 → 不遮挡正常工作 → 长时间伴随 | **开箱可用**；不依赖模型，[桌面 Quick Start](https://airi.moeru.ai/docs/en/docs/manual/tamagotchi/) |
| **实时语音链路** | 麦克风/STT、自动发送、TTS、字幕、试听音色；`v0.11.3` 减少自身语音回灌 → 更自然交流 → 陪聊/轻量 VTuber | **需 STT/TTS/权限，可能付费**；Provider 稳定性不齐，[v0.11.3](https://github.com/moeru-ai/airi/releases/tag/v0.11.3) |
| **多 LLM 与本地端点** | 连接 OpenAI/Claude/Gemini/国内服务及 Ollama、vLLM、SGLang、OpenAI-compatible → 在质量、隐私和成本间切换 → 私有/云混用 | **需 Key、端点或算力**；纯浏览器 WebGPU 推理仍未完成，[Provider 清单](https://github.com/moeru-ai/airi#support-of-llm-api-providers-powered-by-xsai) |
| **官方账号试用** | 邮箱/Google/GitHub 登录后使用带初始电量的官方 Provider → 不先准备 API Key → 快速 Demo | **云服务/额度制**；耗尽后需充值且桌面端不能直接购买，[官方 Provider](https://airi.moeru.ai/docs/zh-Hans/docs/manual/config/providers/consciousness/official) |
| **角色卡与完整角色 ZIP** | 保存人设、场景、提示词与模块，连同支持的显示模型一起导入/导出 → 分享完整角色而非一段 Prompt → 社区创作/迁移 | **`v0.11.3` 已发布**；原始 JSON 已不是主要导入格式 |
| **屏幕捕获/视觉** | 选择窗口或整屏交给视觉模型 → 围绕用户当前内容互动 → 编码/视频/屏幕问答 | **基础可用、偏实验**；需权限与 VLM，主动周期观察仍是 [#2060](https://github.com/moeru-ai/airi/issues/2060) 请求 |
| **跨端交付** | Web/PWA、Windows/macOS/Linux、Android APK、iOS IPA → 先网页试、再安装 → 多设备角色 | 二进制**已发布**，但各端能力与文档不等；主手册仍对应旧版 |
| **游戏/社交接入** | Minecraft、Discord、Telegram 与 Factorio PoC 让角色进入外部环境 → 从陪聊走向共同活动 → 游戏/社群 Agent | **需额外 Bot/服务**；Factorio WIP、Minecraft 有开放连接 Bug，Helldivers 2 未完成 |
| **Artistry 与 MCP** | 接图像生成服务或 MCP Server → 让角色创作并调用外部工具 → 创作/个人助手 | **需外部服务、开发者向**；MCP/插件生态与教程仍早期，[插件提案](https://github.com/moeru-ai/airi/issues/255) |

**同类、易用性与限制：** 相比 [Open-LLM-VTuber](https://github.com/Open-LLM-VTuber/Open-LLM-VTuber)，AIRI 强在 Live2D+VRM、跨端角色包、社交/游戏组合，弱在完整离线和成熟语音打断；相比 [SillyTavern](https://github.com/SillyTavern/SillyTavern)，它更具身，但 Lorebook、长期记忆、群聊和扩展生态明显较弱。UI、在线 Demo、安装包和集中配置是强信号；“self-hosted/you-owned”不等于所有环节离线免费，“看屏幕/玩游戏”也不等于稳定主动 Computer Use 或通用游戏 Agent。

**为何今天关注：** 事实是稳定版仍为 `v0.11.3`，已交付桌面语音增强与携带模型资源的角色 ZIP；推断上，强视觉 Demo、“开源 Neuro-sama/Grok Companion”定位和跨端安装很适合传播。长期/短期记忆、主动视觉、Factorio 完整体验仍应作为跟踪项，而非成品卖点。

### 2. [ECC](https://github.com/affaan-m/ECC)

**一句话定位：** 给 Claude Code、Codex、Cursor、OpenCode 等 AI 编程用户提供可移植的工程工作方式：把规划、TDD、复核、验证、记忆、安全与多 Agent 协作从临时 Prompt 变成可安装组件；它不是模型或推理 Runtime。

**典型场景：** 团队统一 Agent 开发流程；跨 Harness 复用 Skills/Rules；长任务交接与经验沉淀；扫描 Agent/MCP/Hook 配置安全；用 GitHub App 从仓库历史生成项目专属能力。

| Feature | 能做什么 → 用户价值 → 适用场景 | 状态 / 边界 |
|---|---|---|
| **Plan Canvas** | 在本地浏览器渲染计划、Mermaid 与表格，点选批注并批准/退回 → 长计划定位更清楚 → 大功能/迁移评审 | **OSS、`v2.1` 已发布**；是本地单人评审面，不是协作 SaaS，[Release](https://github.com/affaan-m/ECC/releases/tag/v2.1.0) |
| **证据化工程闭环** | Plan→test→implement→review→verify→remember → 降低“写完即宣布完成” → Feature/Bug/上线前检查 | **安装后可用**；流程遵循不等于质量保证 |
| **67 Agents / 281 Skills** | 提供规划、修复、安全、文档、前后端、ML/运维等角色和指南 → 少从零写 Prompt → 多领域开发 | **OSS**；是条目数，不是 281 个独立软件或同等验证能力 |
| **跨 Harness 安装/Sync** | Claude 插件、Codex Sync、Cursor/OpenCode/Gemini/Kimi 等适配，并有 profile/doctor/repair → 降迁移成本 → 混合工具团队 | Claude 最完整；Codex Marketplace 仍实验，手工适配会丢 Hook/命令 parity，[平台矩阵](https://github.com/affaan-m/ECC#platform-support) |

### 9. [FlashKDA](https://github.com/MoonshotAI/FlashKDA)

**一句话定位：** 面向部署 Kimi Delta Attention 模型的推理工程师，把 KDA forward 作为 FLA 可自动选择的高性能后端，重点降低特定长序列 prefill/批处理延迟；它不是完整模型、通用注意力 API 或训练框架。

**典型场景：** KDA 在线/离线推理加速；长上下文 prefill；变长请求合批；带状态的分段计算；目标 GPU 上做后端评测与回归。

| Feature | 能做什么 → 用户价值 → 适用场景 | 状态 / 边界 |
|---|---|---|
| **FLA 自动分派** | 安装后 `fla.ops.kda.chunk_kda` 条件匹配即走 FlashKDA → 业务代码少改 → 既有 FLA 模型 | **可用**；必须 inference mode、bf16、指定形状/flags，[集成 PR](https://github.com/fla-org/flash-linear-attention/pull/852) |
| **Fallback/诊断** | `FLA_FLASH_KDA=0` 回退 Triton，INFO 输出命中/拒绝原因 → 灰度和排错可控 → 上线/A-B | **开箱可用**；必须看日志确认真正加速 |
| **Forward 推理** | FLA 或 `flash_kda.fwd` 执行 KDA 前向 → 专项快路径 → prefill/离线批处理 | **inference-only**；无 backward/autograd，训练自动走其他路径 |
| **固定长度 Batch** | `[B,T,H,D]` 每 batch 独立序列 → 常规合批 → 静态 serving | **可用**；K=V=128、bf16、连续 CUDA 张量 |
| **变长打包** | 用 `cu_seqlens` 合多条请求并保留各自 state → 少 padding → 动态 serving | **可用**；varlen 时 B=1、T 为总长 |
| **Initial/Final State** | 输入/输出 recurrent state → 跨段续算 → 流式/长序列 | **可用**；没有中间 chunk state 或完整 cache 管理 |
| **H20/GB200 基准** | 公布命令、形状、warmup 与逐场景结果 → 可自行复跑 → 硬件验收 | H20 对 FLA Triton 自报 **1.85–2.31×**，GB200 最高 3.27×；特定形状，不是 SLA，[H20](https://github.com/MoonshotAI/FlashKDA/blob/master/BENCHMARK_H20.md) |
| **多架构源码构建** | 自动检测 GPU 或编译 `90a,100a/all` → 同源码覆盖 Hopper/Blackwell → 内部 wheel/镜像 | **需 clone、CUTLASS submodule、CUDA toolchain**；无官方 wheel/Release |
| **Python API/自动 workspace** | wrapper 自动分配临时 workspace、调用者提供 out → 少一项显存管理 → 定制接入 | **当前 `master` 可用、偏底层**；旧 Issue #23 已与现状不符 |
| **正确性测试** | 固定/变长 forward 对照 torch/FLA → 升级前最低验收 → CUDA/PyTorch 回归 | **测试范围窄**；CUDA 13 有失败报告，无广泛 CI 矩阵 |

**同类、易用性与限制：** 最接近的替代是 FLA Triton KDA，而不是标准 FlashAttention。FlashKDA 以极窄条件换专项速度；FLA Triton 支持训练、更多形状/硬件并自然兜底。它没有 UI、CLI、模型级 SDK、预训练模型、Notebook、服务端或官方 wheel。SM90+ 排除常见 Ampere/Ada 消费卡；B=1 64k–512k 的公开 Issue 甚至报告约 0.70× Triton，softplus gate、GVA、context parallel、更多维度均未实现。

**为何今天关注：** 事实是项目有 FLA 无侵入集成、H20/GB200 报告和近期变长/正确性修复，也公开 B=1、CUDA 13 等反例。推断上，KDA/Kimi 关注与高性能数字带来热度；适用人群实际很窄，普通本地模型用户通常既没有相符模型也没有相符 GPU。

| **Benchmark 报告** | dispatch、peak、SRAM、功耗、训练 wall time 与跨 M 芯片社区数据 → 可复测硬件边界 → 研究/选型 | **小样本研究基准**，不是标准 suite |
| **GPU↔ANE Demo** | README 报告零拷贝与 GPU prefill→ANE decode 数字 → 展示异构可能 → 本地 LLM 研究 | **复现性存疑**：README 所列两个 Demo 文件当前 `main` 缺失/404，只能标作者报告 |
| **INT8 W8A8 Benchmark** | 特定深卷积对比 FP16/INT8，M4 自报 1.85–1.88× → 研究带宽收益 → 量化实验 | **单算子基准**；不能外推端到端模型/训练 1.88× |
| **新模型 Header** | 约 15 行配置维度/头数/层数后重新编译 → 较快测新形状 → MHA/GQA 研究 | **手工编译**；不是 HF/ONNX 通用导入器 |
| **C Bridge/直接样例** | in-memory compile/eval、IOSurface I/O、C-callable API → 少从零逆向 → 编译器/Runtime 原型 | **底层实验接口**；无版本化 SDK、稳定 ABI、包发布 |

**同类、易用性与限制：** 与 MLX/PyTorch MPS 相比，ANE 的独有价值是直接训练和测 NPU；MLX/MPS 有成熟 Python/autograd/模型生态，日常训练明显更合适。与 Core ML 相比，它能绕过公开限制做自定义反向研究；Core ML 的稳定部署/App 集成更强。CLI、TUI、两份 README、三篇长文和 benchmark 对 PoC 已很丰富，但 macOS 15+、Apple Silicon、私有 `_ANE*` API 会随 OS 破坏，利用率仅约 5–9% peak，数值稳定还需 loss scaling/CPU workaround。

**为何今天关注：** 事实是 Stories110M、Qwen 短程梯度、checkpoint、TUI 与多类基准均有公开路径，且作者主动写清低利用率、CPU fallback 与非生产边界。推断上，“Mac 里长期只做推理的 NPU 竟能训练 Transformer”极具反直觉传播力；Stars 主要反映研究新颖性，不是大模型训练已实用。

### 12. [book-to-skill](https://github.com/virgiliojr94/book-to-skill)

**一句话定位：** 面向希望在 Copilot CLI、Amp 或 Claude Code 中反复调用书籍/内部文档知识的用户，把 PDF、EPUB、DOCX、网页或文档集编译为可安装 Agent Skill：核心框架常驻，章节/术语按需加载，重点是决策工具而非普通摘要。

**典型场景：** 技术书随编码调用；ADR/Runbook/规范变团队工作规则；论文+笔记持续 Fold-in；品牌/方法论复用；按章节深度学习与复习。

| Feature | 能做什么 → 用户价值 → 适用场景 | 状态 / 边界 |
|---|---|---|
| **结构化 Skill 产物** | 生成核心 `SKILL.md`、逐章、glossary、patterns、cheatsheet → 把书变框架/决策工具 → 技术书/规范 | **稳定流程**；4K/1K tokens 是模板预算，不是硬保证 |
| **渐进加载** | 按 topic/chapter 只载核心与相关章 → 降重复上下文 → 高频参考 | **可用**；是预编译结构，不是原文检索/逐页查证 |
| **多格式/批处理** | 文件、列表、目录、glob；PDF/EPUB/DOCX/TXT/MD/RST/HTML/RTF/MOBI 等 → 少手工统一 → 混合资料 | **可用**；高质量依赖各格式 extractor，MOBI 需 Calibre |
| **技术/文本双模式** | prose 用 pdftotext，技术 PDF 用 Docling 保表格/代码 → 明确速度/保真取舍 → 教材/论文 | **需外部工具**；单样例 103 页 Docling 164s 不代表通用性能，也没有可靠 OCR 基准 |
| **Full/Analyze/Generate/Update** | 完整转换、只分析、从分析生成、增量 Fold-in，生成前展示 token/费用/文件 → 可预审和持续维护 → 大书/研究库 | **可用**；Update 是生成式合并，无冲突 UI/自动同步 |
| **自适应深度** | reference 精简，study 增框架/反模式/worked example → 产物贴近使用意图 → 教学/复杂决策 | **依赖宿主模型判断**；可能遗漏或错误重构 |
| **多宿主 Skill** | 同一 `SKILL.md` 用于 Copilot CLI、Amp、Claude Code，并有 lens validator → 可版本控制、少锁定 → 多 Agent 工具 | `v1.1` **已发布**；各宿主权限/刷新行为不同 |
| **可安装抽取 CLI** | `book-to-skill`/`python -m`、extras 与 `--check` → 脚本化抽取/依赖诊断 → 批处理 | `v1.2` **已发布**；PyPI CLI **只抽文本**，不会独立完成 LLM 生成/注册 Skill |
| **大文档定向读取/测量** | >50K tokens 时先定位章节，并提供 token 模型脚本 → 避免每章重复读全书 → 200–500 页书 | 是执行规范，不是硬保证；供应商缓存/Agent 行为会改成本 |
| **质量/安全扫描** | 要求保留术语、少长篇复制并扫指令覆盖/不可见 Unicode/越权 frontmatter → 降不可信文档变 Agent 指令的风险 → 外部资料 | 扫描位于 `Unreleased`；是 advisory，不验证事实或“无幻觉” |

**同类、易用性与限制：** 相比 NotebookLM，产物可下载、版本控制并直接参与 Agent 工作；NotebookLM 在多源 UI、搜索、答案级引用、音视频概览更强。相比 RAGFlow/普通 RAG，它无需向量库/服务，适合一两本方法密集文档；大规模变化语料、原文 chunk 回溯、引用与权限治理更适合 RAG。相比 Context7，它可处理任意自有文档，但没有自动跟踪上游版本或 MCP 托管索引。项目没有独立 GUI、REST API 或生成 SDK，完整流程需支持 Agent Skills 且能 Shell/读写的宿主模型。

**营销校准与今日原因：** “No hallucination”不成立：LLM 在章节识别、综合、worked example 和回答阶段仍会遗漏/虚构；默认产物没有答案级页码/行号引用。**24–51×**只比较“整本 dump”与约 5K 运行时预算；相对 discovery loop 是 **2.4–15.6×**，未证明答案等质。约 $1/本也是特定模型/价格估算。扫描 PDF OCR 未被单独验证，7 月 28 日 Issue #81 还报告章节计数缺陷。事实是 `v1.1/v1.2` 已完成多宿主、可安装 CLI 与多语结构识别；推断上，“把闲置技术书变 Agent 能力”的直观叙事和大 token 数字推动 +1,421，适合愿意抽样验收输出的早期用户。

### 矩阵结论

- **“Agent 产品层”出现了三种不同答案。** jcode 是运行 Agent 的终端 harness；ECC/Superpowers 是约束其工作方式的 Skill/Hook 层；OpenWork 是把模型、Skill、MCP、SaaS 和团队授权汇成控制面。三者可组合，但重叠安装会增加上下文、权限与维护成本。
- **语音项目也不能只看同一张榜。** speech-to-speech 解决实时管线与客户端协议；VibeVoice 提供模型/推理入口；AIRI 面向角色体验。要做语音伴侣，仍需分别验证模型准确率、首音/打断、Avatar/状态和生产连接。
- **低噪声不等于高召回。** OpenCodeReview 的确定范围/规则很适合第一道筛查，但官方自测自己承认 Recall 低于通用 Agent；Superpowers/ECC 的流程门也只能增强验证证据，不能替代测试、SAST 和人工责任。
- **硬件专项项目的“快”必须和可用域一起读。** FlashKDA 只命中 SM90+、bf16、K=V=128 的 KDA forward；ANE 是 macOS 私有 API PoC。两者都不应被概括成“所有模型更快”或“消费 Mac 能训练大模型”。
- **本地化是分层属性，不是二元标签。** Faceswap 的素材/训练可全本地；speech-to-speech 默认 LLM 仍是云；AIRI/OpenWork 可接本地模型但其他语音、视觉、Connect 或 worker 仍可能出网；敏感使用应画清每个环节的数据路径。

## 今天最值得体验的 3 个项目

1. **[VibeVoice](https://github.com/microsoft/VibeVoice)：优先体验最新 CPU BitNet ASR。** 最吸引人的 Feature 是约 1.58 GB、无 GPU 的 [VibeASR.cpp](https://github.com/microsoft/VibeASR.cpp)，以及基础 ASR 的 Who–When–What 长音频输出。建议拿 10–20 分钟、多人且含专有名词的真实授权录音，分别测无/有 Hotwords 的 WER、speaker 分段、RTF 和内存；不要用官方 10/20 秒短样本替代自己的长音频验收，也不要把已禁用的 90 分钟多人 TTS 当体验重点。
2. **[OpenCodeReview](https://github.com/alibaba/open-code-review)：最适合验证“确定范围 + Agent 判断”的审查方式。** 先用 `--preview` 检查覆盖/排除，再对一个熟悉 PR 分别跑默认模式与 Delegation Mode，比较真实问题、误报、漏报、token 和行号锚定。最吸引人的不是阿里规模叙事，而是可审计规则、JSON/Viewer 与复用现有 Codex/Claude 订阅；把它定位为低噪声首审，不替代人工、测试或高召回安全工具。
3. **[book-to-skill](https://github.com/virgiliojr94/book-to-skill)：最适合把知识验证成可版本控制资产。** 选一本你熟悉、有文本层、章节结构清楚的短技术书，先 Analyze，再生成 reference/study 两版，抽查 Topic Index、worked example、术语和反模式是否忠于原文。它的渐进加载与 Fold-in 很有吸引力，但应主动补页码/原文引用；不要把“24–51×”或“No hallucination”当质量保证。

若目标是直接体验新一代 Coding Agent harness，可把第三名替换为 [jcode](https://github.com/1jehuang/jcode)：重点测 Provider 切换、Swarm 变更通知与跨 Harness resume；关闭/开启本地 embedding 分别量内存，不复述作者的极值倍数。

## 值得持续跟踪的新 Feature 方向

1. **跨宿主 Agent Skill 的能力 Manifest 与逐项兼容测试。** 未来不应只写“支持 10+ Harness”，而要声明 Skills、Hooks、Subagent、MCP transport、UI、权限、更新和恢复分别在哪个宿主可用；ECC、Superpowers、book-to-skill、OpenCodeReview 都暴露了 parity 问题。
2. **从个人工作流到组织能力控制面。** OpenWork 的“一个远程 MCP 输出已授权能力”和 ECC GitHub App 的“仓库历史→PR”显示新方向：能力需要可分发、可撤销、可审计、可计费；关键是本地/Cloud 数据边界、fail-closed、版本回滚和最小权限。
3. **标准兼容的自托管实时语音。** 值得跟踪 Realtime 事件级契约测试、WS/WebRTC parity、打断/取消、工具事件、电话/SIP、多语和 P50/P95，而不是只看“兼容”标签或单次 Demo。
4. **CPU/边缘 ASR 与异构 NPU 的真实工作负载评测。** VibeASR.cpp 需要更长录音、噪声、口音、消费 CPU 与功耗数据；ANE 需要把 PoC 推向稳定公开 API/更高利用率。专项数字必须同时报告准确率、任务完成时间和失败域。
5. **确定性覆盖 + 概率判断的 Agent 质量门。** OpenCodeReview、ECC、Superpowers 都把固定范围/步骤/测试包在模型判断外；下一步应有可复现缺陷集、Recall/Precision、局部失败语义、步骤级 checkpoint 与审计证据。
6. **可追溯的 Agent 记忆与知识编译。** jcode Ambient、ECC Memory Vault、OpenWork cross-chat 和 book-to-skill 处于不同成熟度；真正可用需要来源、时间、置信度、冲突/陈旧检测、人工晋升、答案级引用与可删除性。
7. **具身/多模态 Agent 的权限与状态连续性。** AIRI 已把 Avatar、语音、屏幕、MCP、游戏放在一起；下一步差异会来自可导出记忆、跨设备状态、主动观察频率、工具审批和对外行动的可见审计，而不是再多列几个集成名称。
8. **AI 生成媒体的同意、标识与本地处理安全。** Faceswap/VibeVoice 说明“有伦理声明”不等于有技术保护。值得跟踪授权记录、不可移除来源标记、检测/水印可验证性、平台级披露和本地生物特征数据清理。
9. **专项 kernel 的自动分派证据。** FlashKDA 的拒绝原因日志和显式回退是好方向；未来后端应自动上报命中形状、实际速度/精度、driver/CUDA 兼容，并在不受益时安全回退，而非只展示峰值倍数。
