## 今日 Feature 趋势摘要

1. **Agent Skill 正在形成“通用规范—专业内容—交付工作流”三层。** Anthropic Skills 提供官方能力样例与开放规范入口，Obsidian Skills 把 Markdown/Bases/Canvas/CLI 变为领域能力，Agency Agents 提供角色/SOP，Diagram Design 则直接交付可用视觉成品；四者的功能层级并不相同。
2. **端侧 AI 从“私有推理”进入可行动应用。** Needle 做小模型结构化调用，FluidVoice 将本地语音识别、改写与 Mac 命令结合，Modly 将本地 image-to-3D 做成桌面工作流；真正风险已从模型能否跑转向权限、动作确认、可撤销性与硬件边界。
3. **统一工作区开始争夺 Agent 的共享上下文与操作面。** Macro 把团队邮件/聊天/文档/任务/CRM 变成共享记忆与 MCP；holaOS 把异构 Agent、浏览器、应用、集成、Skills 和本地记忆放进一个桌面工作区。二者都需要区分托管能力、开源自托管能力与企业能力。
4. **“本地模型”产品面在扩张。** Unsloth 不再只强调微调库，而是提供 Desktop/Studio、聊天、RAG、MCP、Coding Agent 接入、训练、导出与 OpenAI-compatible API；LTX-2 则把同步声画生成、控制、精修与训练放进同一套工具。
5. **上下文基础设施正从检索走向可编辑与可问责。** Semantica 强调 decision/provenance/rules/ontology，RAGFlow 强调文档解析、chunk 人工修订、检索测试、引用、Memory 和 Agent workflow；前者偏治理记录，后者偏 RAG 应用工作台。
6. **模型路由仍处成熟度早期。** Switchyard 已能保持原生协议并按内容、阶段或升级策略路由，但 v0.2.0 明确仍是 pre-alpha、not for production；它不能替代完整生产网关的鉴权、配额、预算与运营控制面。
7. **Release surface 漂移依然是采用风险。** Diagram Design、Anthropic/Obsidian Skills、Agency Agents 没有统一 Release/Tag；Needle 只有 tag/PyPI；Unsloth 的 Desktop/Studio 仍 Beta 且 Latest 与最新 tag 不同；holaOS 的 `latest` 滚动发布也难以表达稳定语义。

### 2. [semantica-agi/semantica](https://github.com/semantica-agi/semantica)

**一句话定位：**给需要可追溯 Agent 上下文、知识图谱、决策记录与审计的 AI/数据/合规团队一套自托管 Python 工具箱；它不是 LangGraph/CrewAI 替代品，也不是开箱即用托管 SaaS。

**典型场景：**授信/医疗/法律决策留痕；可追溯 GraphRAG；多 Agent 共享上下文；本体/规则治理；历史时点知识回放。

| Feature | 能做什么 → 用户价值 → 场景 | 状态 / 条件 |
|---|---|---|
| Context Graph / Agent Memory | 把事实、关系、记忆和决策变成可查询图 → 回答“相连什么、当时知道什么” | 本地可用；缺单条 retract/purge，重复 ingest 可膨胀边 |
| [Decision Intelligence](https://github.com/semantica-agi/semantica/blob/v0.6.5/docs/guides/decision-intelligence.md) | 记录理由/结果/先例，追踪因果、影响并做规则门控 → 决策可复核 | Python/MCP/UI 已交付；[#975](https://github.com/semantica-agi/semantica/issues/975) 指显式 CAUSED 边可被 trace 忽略 |
| 双时态/时间旅行 | 区分事实有效时间和记录时间，重建历史状态 → 审计变化而非覆盖旧事实 | v0.6.5 可用；失效闭环仍依赖调用方 |
| 多源摄取与抽取 | 文件、网页、DB、Git、流、Snowflake/Databricks 等经解析/抽取建图 → 少写胶水 | 基础 pattern 无 key；[#973](https://github.com/semantica-agi/semantica/issues/973) 指 DB helper 有直接失败路径 |
| 确定性推理 | forward/Rete/Datalog/SPARQL 给出规则路径 → 政策判断可重复 | 本地可用；复杂 Rete condition matcher 仍有 roadmap 边界 |
| 本体/SHACL/冲突治理 | 管 OWL/SKOS、校验 shape、发现冲突与实体重复 → 减少脏图静默扩散 | 需真实本体/shape 与人工治理；部分 extra |
| [PROV-O 与完整性链](https://github.com/semantica-agi/semantica/blob/v0.6.5/docs/guides/provenance.md) | 记录来源、变更、lineage、hash chain并导出 → 支持调查/审计 | v0.6.5 补齐；证明记录来源不等于来源为真或自动合规 |
| GraphRAG/Hybrid Search | 关系感知切块，融合向量/稀疏/图路径 → 多跳召回更可解释 | 后端结果一致性仍在收敛；需模型/向量库配置 |
| 多图/向量后端 | 接 RDF/LPG/向量库与企业平台 → 从本地 PoC 扩到既有栈 | 多数需外部服务/凭据/费用，后端能力不等价 |
| Knowledge Explorer | 可视审查 graph、timeline、decision、ontology、lineage → 非纯代码用户也能 QA | `explorer` extra；生产必须配置 API key/持久存储 |

| Reference / IC-LoRA | 参考视频/帧做姿态、深度、边缘、风格等 V2V → 结构/运动更可控 | 推理/训练已发；adapter 必须匹配 2.5，不能泛化 2.3 全兼容 |

### 16. [lightningpixel/modly](https://github.com/lightningpixel/modly)

**一句话定位：**给独立创作者、3D 原型设计者和本地 AI 用户一个桌面工作台，把单张图片交给本机 GPU 的开放模型生成 3D mesh，再用节点工作流预览、轻量清理和导出；它不是通用 Agent 或完整 DCC。

**典型场景：**商品/道具草模；游戏/VFX/AR 资产原型；3D 打印初始网格；低代码批量清理流程；Agent/脚本驱动本地生成。

| Feature | 能做什么 → 用户价值 → 场景 | 状态 / 条件 |
|---|---|---|
| 本机单图→3D | 图片经本地扩展生成 mesh并预览 → 素材不上传、无按次云费 | 应用可装；仍需扩展、数 GB 权重、兼容 GPU，单视图背面会猜测 |
| 5 个官方扩展 | Hunyuan Mini/Turbo/Fast、TripoSG、Trellis2 GGUF按速度/质量/显存选 → 不锁单模型 | 恰好 5 个；约6–10GB级只是扩展口径，权重许可各异 |
| Trellis2 几何/纹理解耦 | 先 Generate Mesh，满意后再 Texture Mesh → 少为坏几何浪费纹理成本 | 官方最明确纹理路径；Hunyuan UI 纹理不能按已用宣传，GGUF 权重许可不明 |
| 节点 Workflow/Browser | 串 image/text/mesh/model/process并按文件夹/标签浏览 → 固化重复资产流程 | v0.4.1 可用；模板库远弱于 ComfyUI |
| For Each / While / Wait | 遍历 image/text/mesh、循环和等待分支 → 从单次链扩到批处理 | 已发但年轻；hidden batch 是顺序 helper，不是并发 GPU batching |
| Preflight validation | 跑前检查节点连线并保留当前 mesh → 少在昂贵生成后才失败 | 有价值但社区 object-shaped input 可误判，非强类型保证 |
| Smooth/Decimate/Repair/Remesh | 平滑、控面、简单修洞、triangle/quad-dominant 重网格 → 减少首轮 DCC 清理 | quad-dominant 不是角色 retopology；修洞/UV/细节均有限 |
| Scene viewer / workspace | 选择/变换/基础光照并管理资产 → 不开 Blender 先筛结果 | 已用；无雕刻、UV、材质绘制、rig、animation |
| GLB/STL/OBJ/PLY | 导出 Web/引擎/打印/传统工具链 → 草模可交给下游 | 无 FBX/USDZ/3MF；可写格式不等于拓扑/尺度/材质合格 |
| Extension install / repair | 粘 GitHub URL、选权重、看进度、修损坏 → 降低手配环境门槛 | Beta；仍有 venv/wheel/runtime registration 失败，Marketplace 是 open proposal |
| Canonical Agent CLI | `health/model/workflow-run/capability/process-run` 与 JSON-first `generate` 可查询/取消/恢复 → Agent 不盲点 UI | 需官方 Desktop 正在运行；dev API 不证明 Electron/extension readiness，Comfy helper 明确 experimental |
| 跨平台安装 | Windows exe、Linux AppImage、Apple Silicon dmg + RAM/log/error UI → 更接近消费桌面工具 | 安装包≠全模型跨平台；Intel Mac/AMD未完成，Jetson 非官方 |

**成熟度、同类与缺口：**latest [Beta v0.4.1](https://github.com/lightningpixel/modly/releases/tag/v0.4.1)；[`v0.4.1...main`](https://github.com/lightningpixel/modly/compare/v0.4.1...main) 虽 +8 commits，净差异仅 README，不是 8 项新功能。相比 Blender，Modly 更快得到第一版 mesh，缺生产级建模/retopo/UV/material/rig/animation；相比 ComfyUI，3D viewer/workspace/mesh cleanup/可恢复 CLI 更专注，媒体节点、模板与社区生态更弱；相比 Tripo 云 API，本地隐私/模型可换更强，text/multi-view、retopo、rig/animation、托管 SLA更弱。Modly 自述 MIT，但 LICENSE 额外要求 fork 可见署名，GitHub 为 NOASSERTION；模型许可和输入图片权利须另查。

### 17. [infiniflow/ragflow](https://github.com/infiniflow/ragflow)

**一句话定位：**给需要处理复杂企业文档的知识库与 Agent 团队一个可视化工作台，把解析、可人工纠正的分块、检索评测、引用回答、GraphRAG、Agent、Memory 和对外 API 串成完整产品流程。

**典型场景：**企业知识库问答；扫描件/表格密集 PDF 解析；长文档和多跳关系检索；可视化 Agent 工作流；把带引用的检索/对话能力嵌入现有产品。

| Feature | 能做什么 → 用户价值 → 场景 | 状态 / 条件 |
|---|---|---|
| DeepDoc 与多解析器 | 默认做 OCR、表格/版面识别，也可选 MinerU、Docling、OpenDataLoader 或 VLM → 复杂 PDF 不必先手工清洗 | DeepDoc 开箱可用但较慢；第三方解析器多为 Experimental，需额外依赖/模型 |
| 多格式与数据源 | 接 PDF、Office、图片、网页及多种外部知识源 → 统一汇入知识库 | 文件可直接用；连接器需凭据，源系统权限仍须单独治理 |
| 模板化分块与人工纠正 | 按文档类型解析，UI 修改正文/关键词/问题/标签，API 做 chunk CRUD → 把检索错误落到可修正内容 | 稳定版已交付；未找到 UI 一键任意 split/merge 的一手证明 |
| Parent-child 与 ingestion canvas | 保留父子上下文，并用 parser/chunker/transformer/indexer 画自定义摄取流程 → 兼顾命中精度与上下文完整度 | 已可用；自定义链路需要理解数据与检索目标 |
| Retrieval Test | 展示命中、分数，调阈值、向量/关键词权重、reranker、跨语言及图检索 → 上线前可观察召回 | 已可用；测试页参数不会自动成为所有 Chat/Agent 的统一配置 |
| 引用与原文预览 | 回答附参考 chunk，并回看原文 → 用户能追溯依据、审查知识库 | 已交付；“有引用”不等于答案正确或来源权威 |
| GraphRAG / RAPTOR / PageIndex | 建关系图、层次摘要或页面结构索引 → 支持长文档与多跳问题 | 已用但耗时/耗 token；删除源文档后的图清理和稳定版图导出仍有边界 |
| 可视化 Agent / 多 Agent | 用检索、分类、分支、循环、HTTP/SQL/代码、人类等待、MCP、子 Agent 组装流程 → 非纯代码用户可编排业务 Agent | v0.26.4 已有；稳定文档提示旧 Agent UX 将更新，复杂流程仍需测试和治理 |
| Memory | 管理语义、情景、程序性记忆，支持 retrieval/message、遗忘与共享 → 对话/Agent 可跨轮次保留经验 | 已交付；需 LLM+embedding，默认 5MB 约只容纳 500 条 1KB+1024d 消息 |
| API / SDK / OpenAI 兼容 / MCP | HTTP、Python、兼容 Chat API，既作 MCP client 也能暴露检索工具 → 易嵌入产品和 Agent 宿主 | Stable MCP 实现有 retrieve/list_datasets/list_chats 3 工具，文档仍主要写 retrieve；v0.26.4 有字段兼容 bug |
| Team share / iframe widget | 知识库和应用在团队共享，Chat 可嵌网页 → 快速交付内部/客户入口 | 已用；Only me/Team 粒度较粗，不等于企业 ABAC/细粒度数据权限 |

**成熟度、同类与缺口：**[v0.26.4](https://github.com/infiniflow/ragflow/releases/tag/v0.26.4) 是 7 月 7 日稳定版，真实包含上述 RAG、Agent、Memory 和 MCP；[`v0.26.4...main`](https://github.com/infiniflow/ragflow/compare/v0.26.4...main) 已前进约 1,063 commits，`Operator` 名称来自 tag 后的 [PR #17273](https://github.com/infiniflow/ragflow/pull/17273)，不能把它写成稳定版成熟功能。自托管最低建议 4 CPU/16GB RAM/50GB 磁盘、Docker 24+/Compose 2.26.1+；预构建镜像以 x86 为主，ARM 要自行构建；v0.22 起不再内置 embedding model，切换 embedding 还需删 chunk 重建。相比 Dify，RAGFlow 的文档解析、chunk 检查、检索测试和图检索更深，通用 App 市场/运营弱；相比 AnythingLLM 更重但复杂文档可控性强；相比 LlamaIndex 低代码产品面更完整，代码可组合性、评测/连接器广度较弱。另有 v0.26.4 MCP 字段 bug、粗粒度权限、GraphRAG 成本和 UI 迁移风险。

**今日关注：****事实**：榜单 #17、+465；v0.26.4 已覆盖复杂文档到 Agent/Memory/MCP 的稳定链路，main 仍高速演进。**推断**：复杂 PDF→检查/修 chunk→检索测试→引用回答的可复现闭环，比抽象“企业 RAG”更有说服力；Operator/agentic search 预期也可能带来关注，但尚不能算稳定版现成功能。

## 今天最值得体验的 3 个项目

1. **[Diagram Design](https://github.com/cathrynlavery/diagram-design)**：今天最低成本、最容易马上验证价值的项目。用同一段内容试 draw.io 与 Mermaid 重绘，再切换 audience/size/detail；真正吸引人的不是“画图”，而是语义选型与可编辑交付物。注意实际是 27 类且没有正式 Release。
2. **[Unsloth](https://github.com/unslothai/unsloth)**：最完整的本地模型产品面。从 Unsloth Start 试 GGUF 对话，再体验 RAG/Data Recipes；有 GPU 再进训练与导出。安装时把带资产的 v0.1.701-beta 与无资产的 v0.1.702-beta 修复边界分开看。
3. **[Modly](https://github.com/lightningpixel/modly)**：最具“看一眼就懂”效果的新方向。优先测试 Trellis2 的几何先行、纹理后置流程，以及 Desktop 在线时的 canonical Agent CLI；把结果当 Blender/游戏资产管线的草模入口，不要当生产级 retopo/rigging 替代品。

若更关心 Agent 基础能力而非视觉工具，优先替换体验 **[Needle](https://github.com/cactus-compute/needle)**：它能快速验证设备端 grammar-constrained function calling，但务必在模型输出与真实动作之间自己加权限、确认和策略门。

## 值得持续跟踪的新 Feature 方向

- **Skill 的能力契约：**不只分发 Markdown，还需明确兼容宿主、允许工具、依赖、许可、版本和可复现测试；今天三个 Skills 类项目同时暴露这一缺口。
- **端侧动作安全：**小模型 function calling 与桌面 Command 正变得可用，下一阶段价值在 confidence gate、最小权限、逐动作确认、审计和回滚，而不是再多一个 shell tool。
- **共享上下文的可迁移治理：**Macro、holaOS、RAGFlow、Semantica 都在争“长期记忆/上下文”，应持续看来源追踪、权限继承、删除语义、导出格式和跨工具可迁移性。
- **路由从分数走向任务阶段：**Switchyard 的 stage-aware 思路值得看，但生产价值要等鉴权、provider failover、成本账本、策略解释与回放补齐。
- **人能纠正的 RAG 中间产物：**可看/改 chunk、单独做 retrieval test、回原文的能力，比不可观察的“一键知识库”更能建立可靠性。
- **本地多模态输出继续可编辑：**LTX 的 Retake/关键帧与 Modly 的几何/纹理分阶段说明，用户要的不是一次生成，而是局部重做、交给标准工具继续编辑和质量检查。
- **Release surface manifest：**tag、安装包、README、文档、模型权重和 hosted 产品经常不同步；值得出现机器可读的“这一版本究竟可用什么”清单。
